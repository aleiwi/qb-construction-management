# خطة النشر العام وبوابة الدخول والصلاحيات

**الإصدار:** 1.0 | **التاريخ:** 2026-08-19 | **الحالة:** معتمدة للمراجعة

---

## 1. الفكرة ورأي التقييم

**الفكرة:** نشر النظام عبر بوابة تسجيل دخول، ربط المستخدمين بأرقامهم البريدية، وتفعيل نظام صلاحيات متدرج.

**التقييم المهني:**
- الفكرة سليمة والاتجاه صحيح، والنظام **مبني بالأساس لدعمها** (JWT + 5 أدوار + RBAC في الـ backend).
- الوضع الحالي يكفي للاستخدام الداخلي التجريبي، لكنه **غير جاهز للنشر العام** — النواقص الحرجة: لا يوجد تفعيل بريد إلكتروني، لا يوجد استعادة كلمة مرور، لا توجد دعوات مستخدمين، صلاحيات الأدوار عامة (غير محددة على مستوى المشروع/السجل).
- التوصية: تنفيذ المراحل بالترتيب أدناه؛ المراحل 1–2 شرط مسبق للنشر، المراحل 3–4 تُرفع تدريجياً بعد الاستقرار.

---

## 2. الوضع الحالي (ما هو موجود)

| البند | الحالة | التفاصيل |
|---|---|---|
| مصادقة JWT | ✅ موجود | Access 24h + Refresh 7d |
| الأدوار | ✅ موجود | admin, project_manager, engineer, accountant, contractor |
| RBAC على الـ API | ✅ موجود | `require_roles` على كل endpoint |
| عزل المقاول | ✅ جزئي | المقاول يرى سجلاته فقط (enforced في الـ route) |
| Audit log | ✅ موجود | تسجيل العمليات المالية والإدارية |
| Docker + CI/CD | ✅ موجود | compose + GitHub Actions |
| تفعيل البريد | ❌ ناقص | لا يوجد إرسال بريد إطلاقاً |
| استعادة كلمة المرور | ❌ ناقص | لا توجد آلية reset |
| دعوات المستخدمين | ❌ ناقص | الإدمن ينشئ الحسابات يدوياً فقط |
| صلاحيات على مستوى المشروع | ❌ ناقص | الأدوار عامة على كامل النظام |
| Rate limiting | ❌ ناقص | لا حماية من هجمات التخمين |
| تعطيل الإدمن الافتراضي | ❌ ناقص | admin@qb.com/admin123 ما زال مفعلاً |

---

## 3. الأهداف

1. نشر النظام على نطاق عام (دومين + HTTPS + Docker) بشكل آمن.
2. بوابة دخول واحدة لكل المستخدمين عبر البريد الإلكتروني + كلمة المرور.
3. ربط كل مستخدم بعنوانه البريدي (تفعيل الحساب، استعادة كلمة المرور، إشعارات).
4. نظام صلاحيات متدرج: أدوار عامة + عزل على مستوى المشروع + سجلات تدقيق كاملة.

---

## 4. المراحل والتنفيذ

### المرحلة 1 — جاهزية الإنتاج (Production Hardening)
**الهدف:** إغلاق الثغرات الأمنية قبل أي نشر.

- [x] Rate limiting على `/auth/login` و `/auth/refresh` (5 محاولات/دقيقة + قفل حساب 15 دقيقة بعد 5 إخفاقات).
- [x] قفل الحساب بعد محاولات فاشلة + سجل Audit log للحالات.
- [x] تعيين `Access-Control-Allow-Origin` على الدومين الفعلي فقط (الإنتاج).
- [x] إزالة `--reload` والـ debug من وضع الإنتاج.
- [x] فرض HTTPS فقط (redirect من HTTP) + TrustedHost middleware.
- [ ] تعطيل المستخدم الافتراضي `admin@qb.com` بعد إنشاء أدمن حقيقي (حارس الإقلاع يرفضها حتى يُنشأ أدمن حقيقي).

### المرحلة 2 — النشر العام (Go Live)
**الهدف:** تشغيل النظام على دومين حقيقي.

- [ ] شراء دومين (مثال: `qb.example.com`) وربطه بـ DNS.
- [ ] توفير سيرفر (VPS أو خدمة سحابية) بنظام تشغيل Linux + Docker.
- [ ] إعداد Nginx (أو Traefik/Caddy) كـ Reverse proxy مع شهادة HTTPS مجانية (Let's Encrypt).
- [ ] تشغيل `docker compose up -d` بنسخة الإنتاج (PostgreSQL).
- [ ] تهيئة النسخ الاحتياطي اليومي لقاعدة البيانات + رفعها لمكان خارجي (S3/Drive).
- [ ] كتابة runbook: كيف نرصد، نعيد التشغيل، نطبق تحديثاً (مرفق في `HOW_TO_DEPLOY.md`).

### المرحلة 3 — البريد والتفعيل واستعادة كلمة المرور
**الهدف:** ربط كل مستخدم ببريده الإلكتروني فعلياً.

- [x] خدمة SMTP في الـ backend (مع Console fallback للتطوير — يُسجَّل `[EMAIL-DEV]`).
- [x] **تفعيل الحساب:** عند إنشاء مستخدم → إرسال رابط تفعيل صالح 24 ساعة → المستخدم يضع كلمة مروره بنفسه.
- [x] **استعادة كلمة المرور:** رابط reset عبر البريد، صالح 30 دقيقة، استخدام لمرة واحدة.
- [ ] تحديث حالة الحساب: `pending` → `active` → `disabled` (نموذج جاهز في `User.is_active`).
- [ ] إشعارات اختيارية (تسجيل دخول جديد، تغيير كلمة المرور).

### المرحلة 4 — نظام الدعوات وربط الصفحات بالأيميل
**الهدف:** التحكم الكامل بمن يصل إلى ماذا.

- [x] **لوحة إدارة المستخدمين** (إدارة كاملة: إنشاء، تعطيل، تفعيل، تغيير الدور، إعادة إرسال الدعوة).
- [x] **دعوات بالبريد:** الإدمن يدخل إيميل الشخص + دوره → يصله بريد فيه رابط لإنشاء الحساب.
- [x] **ربط المستخدم بالمشروع:** جدول `user_projects` (user_id + project_id) — من يضاف لمشروع يرى صفحاته فقط.
- [x] **منح وصول للمقاول:** ربط حساب المقاول بالسجلات المملوكة له تلقائياً عند الربط (إنشاء مستخدم أو سجل مقاول بالبريد نفسه + فلترة عقوده/مدفوعاته).
- [x] **لوحة المستخدم (Profile):** تغيير كلمة المرور، البريد، الاسم — مع تسجيل كل تغيير في Audit log.

### المرحلة 5 — نموذج الصلاحيات الكامل (RBAC + RLS)
**الهدف:** صلاحيات دقيقة على مستوى المورد.

| الدور | المشاريع | المخططات/BOQ | المدفوعات | تقارير/KPI | المستخدمون |
|---|---|---|---|---|---|
| admin | كل شيء | كل شيء | كل شيء | كل شيء | إدارة كاملة |
| project_manager | مشاريعه فقط | كل ما يخص مشاريعه | اعتماد/مراجعة | مشاريعه | قراءة الأدوار |
| engineer | المخصصة له | تحرير المخططات/BOQ | — | مشاريعه | — |
| accountant | المخصصة له | قراءة | إنشاء/اعتماد المدفوعات | مالية | — |
| contractor | مشاريعه فقط | سجلاته فقط | حالة مدفوعاته فقط | سجلاته فقط | — |

- [x] تطبيق فحص `project_id` في كل endpoint يخص مشروعاً (`check_entity_access` يحل كل كيان إلى مشروعه — لا يُكتفى بالدور العام).
- [ ] فرض نفس القواعد في الـ frontend (إخفاء الأزرار/الصفحات) مع بقاء الـ backend هو المرجع.
- [x] اختبارات RLS لكل وحدة (`tests/test_rls.py` — 8 اختبارات منع عبر المخططات/العقود/المدفوعات/الجودة/التقارير).

## 6. المخاطر والتخفيف

| المخاطرة | الأثر | التخفيف |
|---|---|---|
| تعطّل إرسال البريد | لا يمكن إنشاء حسابات | SMTP ثانوي احتياطي + إعادة المحاولة تلقائياً |
| تخمين كلمات المرور | اختراق حسابات | Rate limit + قفل الحساب + كلمة مرور قوية إجبارية |
| تسريب بيانات مقاول إلى آخر | خرق عزل | فحص project_id في الـ backend + اختبارات RLS |
| تعطل السيرفر | توقف الخدمة | النسخ الاحتياطي اليومي + runbook استعادة |
| الإدمن الافتراضي | وصول كامل غير مراقب | تعطيله فور إنشاء أدمن حقيقي |
| صلاحيات واسعة | وصول غير مبرر | مراجعة دورية للأدوار + Audit log |

## 7. معايير القبول (قبل إعلان الإطلاق)

- [ ] تسجيل مستخدم جديد من البريد يعمل من طرف لطرف (دعوة → تفعيل → دخول).
- [ ] استعادة كلمة المرور تعمل وتعطّل الرابط القديم.
- [ ] المقاول الجديد **لا يستطيع** رؤية أي سجل لا يخصه (اختبار عملي + آلي).
- [ ] لا يمكن تخمين كلمة المرور (قفل بعد 5 محاولات).
- [ ] الموقع يعمل على HTTPS فقط، والنسخ الاحتياطي اليومي مثبت استعادته مرة واحدة على الأقل.
- [ ] كل العمليات الحساسة تظهر في Audit log.
- [ ] `pytest` كامل أخضر (الاختبارات الحالية + الجديدة).
